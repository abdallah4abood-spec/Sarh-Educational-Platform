# استراتيجية ترحيل قاعدة البيانات — التوصية

**التاريخ:** 2026-10-22.
**النطاق:** `prisma/schema.prisma`، `package.json`، سكربتات الإعداد، وREADME. لا تغيير
على الإنتاج ولا إنشاء baseline في هذه المرحلة.

---

## 1. الواقع الحالي

| العنصر | الحالة |
|---|---|
| محرك قاعدة البيانات | PostgreSQL |
| ORM | Prisma 6 |
| `prisma/migrations` | **غير موجود** |
| أمر التطوير المعتمد | `npm run db:push` → `prisma db push` (بلا سجل) |
| Seed | `npm run db:seed` → `tsx prisma/seed.ts` |
| ملفات نشر (Docker/Vercel/CI) | لا توجد في المستودع |
| النشر العام | لا يوجد نشر مباشر موثق في README |
| حالة مخطط التطوير | `prisma migrate diff` بين قاعدة التطوير والمخطط يعطي **«This is an empty migration»** |

هذا يعني أن قاعدة التطوير الحالية متوافقة مع المخطط، لكن لا يوجد تاريخ تغييرات
قابل لإعادة التشغيل على قاعدة أخرى.

---

## 2. المقارنة

| المعيار | `db push` + SQL موثق | Prisma Migrate + baseline |
|---|---|---|
| إعادة إنتاج قاعدة جديدة | ممكنة عبر `db push` + seed | ممكنة عبر `migrate deploy` |
| قاعدة موجودة | SQL يدوي/runbook | يحتاج baseline ثم `migrate resolve` |
| سجل التغييرات | لا يوجد | موجود |
| خطر الانحراف | مرتفع مع نمو الفريق | أقل |
| خطر الآن | منخفض إذا بقي في التطوير | **مرتفع** لعدم وجود نسخة إنتاج/اختبار مطابقة |
| التراجع | SQL معاكس موثق | migration أو SQL معاكس |
| مناسب لحالة المشروع | **نعم الآن** | لاحقًا بعد تثبيت بيئة حقيقية |

---

## 3. التوصية الواحدة

**لا ننتقل إلى Prisma Migrate الآن.** نُبقي `prisma db push` للتطوير والاختبار،
ونعتمد SQL إضافيًا مراجعًا وموثقًا لأي بيئة موجودة (اختبار/إنتاج)، ثم نُنشئ baseline
حقيقيًا فقط بعد الحصول على نسخة/استنساخ من قاعدة الإنتاج والتحقق من تطابقها.

**السبب:** المستودع لا يملك migrations ولا إعداد نشر، و`db push` على قاعدة موجودة قد
يُسقط أعمدة أو يعيد كتابة أنواع دون سجل. إنشاء baseline من قاعدة التطوير الحالية
سيخمّن أن الإنتاج مطابق لها، وهذا غير مثبت. SQL الإضافي (`ADD COLUMN` + `UPDATE` +
`CREATE INDEX`) أقل مخاطرة، ويمكن التحقق منه داخل معاملة وتراجعه.

---

## 4. خطة التنفيذ

### أ. قاعدة جديدة (تطوير/اختبار)

1. أنشئ قاعدة فارغة مخصصة للاختبار.
2. ضع عنوانها في `DATABASE_URL` المؤقت (لا تكتبه في السجلات).
3. `npx prisma db push` ثم `npm run db:seed` إن كانت البيانات التجريبية مطلوبة.
4. تحقق من الأعداد: 5 `CENTER_ADMIN`، 1 `SUPERVISOR`، 8 `TEACHER`، 0 `SECRETARY`،
   0 `STAFF`.
5. شغّل `npm test`, `npx tsc --noEmit`, `npm run build`.

### ب. قاعدة موجودة (اختبار ثم إنتاج، عند الطلب فقط)

1. **نسخة احتياطية:** `pg_dump` كاملة، والتحقق من إمكانية استعادتها على قاعدة منفصلة.
2. **مقارنة:** `prisma migrate diff --from-schema-datasource ... --to-schema-datamodel ...`
   على استنساخ، وليس على الإنتاج مباشرة.
3. **تطبيق SQL** من `staff-role-rollout.md` داخل معاملة واحدة، بعد مراجعة الخريطة.
4. **التحقق:** `role IS NULL` = 0، الأعداد 5/1/8/0/0، والفهرس موجود.
5. **النشر:** انشر الكود الذي يقرأ `role` بعد نجاح الخطوة السابقة.
6. **الدخان:** تسجيل دخول مالك، مدير غير مالك، معلم، ومدير مُلغى؛ لا بيانات مالية
   لغير المالك.
7. **التراجع:** أعِد نشر النسخة التي لا تقرأ `role` أولًا، ثم نفّذ SQL التراجع
   (حذف الفهرس والعمود والنوع). لا تحذف عضويات أو عناوين.

### ج. متى ننتقل إلى baseline؟

- عند وجود قاعدة إنتاج/استييج حقيقية يمكن استنساخها.
- عند وجود أكثر من بيئة أو أكثر من مطوّر يغيّر المخطط.
- عند الحاجة إلى سجل تدقيق للتغييرات أو نشر آلي.

الخطوات المقترحة حينها:

1. استنساخ قاعدة الإنتاج إلى قاعدة منفصلة.
2. توليد migration أولية من المخطط الحالي:
   `prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`.
3. وضعها في `prisma/migrations/0_init/migration.sql` ومراجعتها.
4. على الاستنساخ: `prisma migrate resolve --applied 0_init` ثم `prisma migrate deploy`.
5. التحقق من عدم وجود diff، ثم تطبيق نفس الخطوات على الإنتاج بعد backup.
6. تحويل CI/النشر إلى `migrate deploy`، وإبقاء `db push` للتطوير المحلي فقط.

**لا تنفّذ الخطوة 3-5 قبل وجود استنساخ مطابق. لا تنشئ baseline من قاعدة التطوير
وتفترض أنه يطابق الإنتاج.**

---

## 5. المخاطر والضوابط

| الخطر | الضابط |
|---|---|
| `db push` يعدّل/يحذف بيانات في بيئة مشتركة | ممنوع على الإنتاج؛ SQL فقط بعد backup |
| انحراف المخطط بين البيئات | `migrate diff` قبل كل نشر + تحقق من الأعداد |
| تطبيق SQL مرتين | السكربت ليس idempotent للـUPDATE؛ نفّذه مرة واحدة وسجّل التنفيذ |
| نسيان rollback | SQL تراجع موثق مع ترتيب: كود أولًا ثم عمود |
| تعذر الاتصال بقاعدة أثناء الفحص | الفحص الحي يفشل مغلقًا؛ لا يمنح وصولًا |

---

## 6. ما لم يُنفّذ

- لم يُنشأ `prisma/migrations` ولا baseline.
- لم يُنفّذ `db push` أو SQL على الإنتاج.
- لم يتغيّر أي إعداد نشر.
- لم تُحذف بيانات التطوير.
