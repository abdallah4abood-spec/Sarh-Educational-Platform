# ربط الطالب بولي الأمر — المرحلة 4.3

**التاريخ:** 2026-10-26.
**الحالة:** الكود والاختبارات منفَّذة على قاعدة اختبار منفصلة. قاعدة `sarh_db`
الأصلية **لم تُلمس** في هذه المرحلة: لا `db push`، ولا migration، ولا seed.
**المراحل السابقة:** 4.0 (القدرات)، 4.1 (رمز الانضمام)، 4.2 (طابور الطلب).

---

## 1. القرار المعماري

الوصول إلى سجلات الطفل **منحة لكل مؤسسة**، وليس حالة على الرابط الأسري:

```
StudentGuardian            العلاقة الأسرية + isPrimary
  └─ StudentGuardianGrant  صلاحية قراءة (طفل × مؤسسة) بحالة APPROVED
```

- `StudentGuardian.status` ملخّص عرض فقط، وليس بوابة صلاحية.
- `Student.parentId` لا يُقرأ في أي مسار وصول.
- اعتماد مركز A لا يفتح سجلات المركز B حتى لو كان الطفل مسجّلاً فيهما.
- سحب منحة A لا يمسّ منحة B ولا يغيّر `isPrimary`.
- الطفل الذي له رابط أسري بلا منحة يظهر **بطاقة هوية فقط** («غير مسجل في مؤسسة»)،
  ولا تُقرأ له يومية أو درجة أو إعلان أو جهة اتصال.

## 2. مصدر الصلاحية

```
resolveGuardianAccess(userId)
  ├─ الحساب موجود
  ├─ طبقة PARENT حيّة (role أو roles)
  ├─ البريد موثّق
  ├─ grants: StudentGuardianGrant.status = APPROVED, link.userId = userId
  └─ linkedStudentIds: StudentGuardian.status = APPROVED (هوية فقط)
```

`studentIds` مشتقة من المنح المعتمدة حصراً. `linkedStudentIds` تُستخدم لبطاقة
الهوية، ولا تُمرَّر إلى أي استعلام بيانات مؤسسية.

## 3. دورة حياة المنحة

```
(لا منحة) --رمز جديد--> PENDING     (لا وصول، حدث REQUESTED)
PENDING   --اعتماد--> APPROVED      (وصول لهذه المؤسسة)
PENDING   --رفض-----> REJECTED      (لا وصول، السجل يبقى)
APPROVED  --سحب-----> REVOKED       (يتوقف الوصول فوراً)
REJECTED/REVOKED --رمز جديد--> PENDING (إعادة فتح، بلا تغيير isPrimary)
PENDING/APPROVED --رمز جديد--> نفس الحالة (idempotent، لا حدث جديد)
```

كل انتقال يكتب `StudentGuardianEvent` داخل المعاملة نفسها. مفاتيح المنع من
التكرار: `grant-request:<codeId>` و`grant-decision:<requestEventId>`.

### قاعدة `isPrimary`

- تُعيَّن **مرة واحدة** عند أول اعتماد لرابط لا يملك أساسياً آخر، أو عند إنشاء
  الرابط من ولي الأمر نفسه.
- لا تتغيّر عند اعتماد منحة إضافية، ولا عند الرفض، ولا عند السحب، ولا عند إعادة
  الطلب.
- اختيار جهة الاتصال في كشوف المؤسسة يُقرأ من **منح تلك المؤسسة فقط**:
  `isPrimary` أولاً، ثم أقدم `approvedAt`، ثم `id` كفاصل حتمي — دون أي كتابة أثناء
  القراءة.

## 5. مسارات القراءة المعزولة

| المسار | القيد |
|---|---|
| `loadChildLogs` | `(studentId, institutionId)` من المنح المعتمدة |
| `loadChildrenOverview` | الأداء واليوميات مقيدة بمنح الطفل |
| `loadParentDashboard` | الإعلانات: عام + مؤسسات المنح فقط |
| `loadFeedChildren` | تسجيلات مؤسسات المنح فقط؛ غير المسجّل يبقى هوية |
| كشف المعلم | جهة الاتصال من منح **مؤسسة الصف** فقط |
| `/api/parent/ai-chat` | لا يُرسل أي اسم طفل أو مؤسسة أو صف أو درجة |

**إصلاح الإعلانات:** عند عدم وجود منح، الاستعلام `{ institutionId: null }`
فقط. لا يُستخدم `{}` داخل `OR` لأنه يطابق كل الصفوف ويوسّع الوصول.

## 6. المخطط

- `StudentGuardianGrant` جديد، فريد على `(linkId, institutionId)`.
- `SubjectPerformance.institutionId` **NOT NULL** مع `onDelete: Restrict`.
- لا تغيير على `Enrollment` أو العمولات أو `PaymentStatus`.

الترحيل يتم على مرحلتين: إضافة العمود اختيارياً وتعبئته والتحقق، ثم فرض
`NOT NULL`. التفاصيل والأوامر في
[`phase-4.3-migration-and-recovery.md`](./phase-4.3-migration-and-recovery.md).

## 8. مخاطر متبقية

| الخطر | الضابط |
|---|---|
| مركز يعتمد حساباً ليس لولي أمر الطفل | تحقق بشري + إفصاح + سجل تدقيق |
| `isPrimary` غير مفروض بفهرس جزئي | الكتابة تحت قفل `guardian-primary:<studentId>` |
| ترحيل 32 صفاً بلا مؤسسة | سكربت يجهض قبل أي كتابة عند صف غير قابل للإسناد |
| استعادة كاملة تفقد بيانات ما بعد الترحيل | نسخة pre/post + تقرير فروق قبل أي استعادة على `sarh_db` |
| تراجع الكود بعد الترحيل | الكود القديم لا يقرأ المنح؛ الرجوع محظور إلا بعد نجاح بوابة الأمان |

## 9. غير المنفَّذ عمداً

- لا `db push` ولا migration ولا seed على `sarh_db` في هذه المرحلة.
- لا `commit` ولا `push`.
- لا إشعار بريدي للطرف الآخر.
- لا حدّ محاولات موزّع (العدّاد داخل العملية فقط).
